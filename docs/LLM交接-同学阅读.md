# LLM 模块交接说明——给负责接入的同学

版本：2026-10-15 · 对应项目总体开发流程 V3.0
项目：基于多源视觉感知与智能优化的校园交通出行服务系统

## 1. 你的任务

负责网页中的“AI 出行助手”：把自然语言变成结构化出行需求，调用后端业务工具，根据工具返回的数据解释方案。WorkBuddy 中使用 DeepSeek 是开发方式，不代表产品后端已经拥有 DeepSeek API 权限或密钥。产品使用的云模型由项目负责人开通百炼后提供配置；代码应允许替换服务商、地址和模型名。

负责范围：LLM 接入、对话接口、停车/路线/公交工具适配、偏好解析、助手界面、错误处理和联调文档。不负责训练 YOLO、调整视觉识别算法、采集地图道路数据或编写路径优化核心算法。不要为了完成对话展示，虚构道路、公交线路、时刻或停车空位。

## 2. 项目真实状态（已按代码核对）

|模块|现状|你可以怎么用|
|---|---|---|
|前端|Vue 3 + Vite + Leaflet，已有地图、停车、人车识别等页签|在现有项目加助手，不重新搭建网站|
|后端|FastAPI，入口 backend/app/main.py|新增路由并挂载 /api|
|停车区|从 data/parking.imported.geojson 读取用户提供的多边形|按已有 id 和 name 查询，不能自行重命名|
|停车状态|每 15 秒变化的模拟数据|回答必须注明“模拟”，保留更新时间|
|道路/公交|返回 not_configured，尚无可计算网络|明确提示未接入；等待算法同学提供服务|
|路线接口|POST /api/routing/plan 返回 HTTP 501|接入时不能把它当成已经可用|
|视觉|本地 YOLO 上传测试，存在明显漏检|候选检测数不能当作可靠停车占用或准确空位|
|SQLite|V3.0 计划项，当前业务尚未接入|不要假定数据库、表和迁移已经存在|
|Compose|当前只有 frontend、backend 两个服务|独立 vision 服务是后续计划；基础后端镜像不包含视觉依赖|
|LLM|尚未实现|这是本次交接需要新增的模块|

GeoJSON 中 is_example=false 仅表示用户提供的数据，并不代表点位或容量经过实测核验。真实业务数据与模拟数据必须分别标注。

## 3. 已有接口与运行入口

- GET /api/health：后端健康状态，parking_mode=simulated。
- GET /api/parking/areas：停车区 FeatureCollection，属性包含 id、name、capacity。
- GET /api/parking/status：mode、is_example、updated_at、refresh_seconds、items；每项含 id、capacity、occupied、available、state。
- GET /api/parking/{area_id}/status：查询指定区域，不存在时 404。
- GET /api/roads、GET /api/transit：当前未配置。
- POST /api/routing/plan：请求含 origin、destination，各为 longitude、latitude；当前 501。
- GET /api/vision/observations：视觉候选结果，不能直接替代模拟停车状态。

本地后端 8000；开发前端常用 5174，Mac 脚本默认 5173；Vite 已将 /api 转发给本地后端。Compose 网页是 http://127.0.0.1:8080，前端 Nginx 将 /api 转发到 backend:8000。

在项目根目录执行 docker compose up -d --build，随后访问网页和 http://127.0.0.1:8000/docs。需要 Docker 环境；现有 Compose 文件不等于已在所有平台验证成功。Mac 本机运行方法见 START-HERE-MAC.md。

## 4. 先完成的小闭环

第一步：用户问“现在有哪些停车区有空位？”→ 后端调用停车工具 → 返回当前模拟空位、区域名称和更新时间。
第二步：用户说“我要去修远楼，少走路”→ 解析目的地、偏好；如果没有起点，继续询问；如果地点不能映射到已核验目录，展示候选或请用户地图选点。
第三步：路线/公交未接入时说明限制；接入后调用实际算法，把推荐停车区、骑行段、步行段、公交段交给地图展示。
第四步：“尽量少走路、避开拥堵、不要公交”等追问能更新之前的条件，再执行规划，而不是只改回答文字。

助手不能自己推算最短路、编造预计分钟数或把两点直线称作校园可通行路线。路线和排序来自算法模块，LLM 负责需求理解与解释。

## 5. 和其他同学的接口协作

|交接对象|需要对方提供|你交付给对方|
|---|---|---|
|项目负责人|百炼服务地域、实际模型 ID、后端密钥配置方式、费用上限|配置模板、调用记录的 token 用量和错误说明|
|路线算法同学|地点目录、坐标、可通行路网、停车联合推荐的结构化结果|起终点、出发时间、允许方式和用户偏好|
|公交同学|站点/线路/时刻、候车假设、步行和公交方案|同一出行请求，以及统一路线展示要求|
|视觉同学|带来源、时间、质量状态的识别结果|只读调用需求；不要直接改识别流程|
|前端/集成同学|地图选点和路线绘制的对接方式|助手面板、结构化结果、模拟/缺失数据提示|

建议新建 POST /api/assistant/chat；详细的建议协议写在 AI 版交接文档中。这是待实现协议，不是现有接口。请先与算法/前端同学确认，不要悄悄修改旧 /routing/plan 的请求格式。

## 6. 百炼配置与密钥

建议后端变量：LLM_PROVIDER、LLM_BASE_URL、LLM_MODEL、LLM_API_KEY、LLM_TIMEOUT_SECONDS、LLM_MAX_TOOL_ROUNDS。服务地址与模型名以负责人账户所在地域和控制台为准，不照抄其他地域配置。

只提交不含密钥的 .env.example。密钥放本机 .env，确保被 Git 忽略，并通过 Compose environment 或 env_file 显式注入后端；Compose 的 .env 不会自动把所有变量传入容器。本机 python run_backend.py 也不会自动读取 .env，须实现加载或在终端设置变量。

不要使用 VITE_ 前缀保存密钥，不把密钥发送给浏览器、截图、聊天记录或日志。初期仅发送用户文本和必要交通结构化数据，视觉照片/视频 API 接入属于另一个模块。
