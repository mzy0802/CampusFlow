# 交通动画性能方案与本轮调整

更新 2026-10-17。

## 为什么设备没满仍会掉帧

浏览器页面的 JavaScript、DOM 更新与部分 Canvas 提交集中在主线程。整机平均 CPU 或 GPU 占用不高，并不代表这条线程还有足够的每帧预算。当前路径算法只在加载时由后端计算；将这部分搬上云端不会直接解决前端逐帧绘制卡顿。帧率要通过浏览器性能记录和不同缩放等级测量，不能用整机占用率证明渲染没有瓶颈。

## 可选方案

|方案|保留的体验|取舍与实施范围|
|---|---|---|
|优化现有 Canvas 交互动画|地图缩放、选区、时间轴、路线和人数调试|改造最小；减少重绘、复用轨迹、缓存静态层。仍由浏览器绘制，需要实际设备测试|
|WebGL 批量绘制卡通精灵与轨迹|完整交互、更多动态对象|适合长期方向。将对象位置与图片纹理批量提交 GPU，需要重构渲染器；DOM 停车标签仍单独处理|
|预渲染 MP4/WebM|稳定的答辩演示，播放、暂停、进度|预先生成全景与近景镜头，本机主要解码播放。无法保持任意地图视角和逐对象交互，缩放视频会损失细节|
|混合模式|交互地图用于操作、预渲染影片用于完整演示|稳定展示和自由探索分开，需维护两套展示入口与素材|

推荐：正式交互产品选 WebGL，答辩备用可增加预渲染影片。服务器实时渲染再推送视频也是选项，但增加带宽、延迟、服务器资源和维护成本；“完全动画”仍需要本机播放，不等于没有本地计算。

目前未擅自改成视频或 WebGL。本轮先完成低风险 Canvas 减负，保留以后替换渲染器的路径/队列数据协议。

## 本轮已做的减负

- 静态停放车辆、动态轨迹、移动人物分为三个 Canvas 图层。
- 停放车辆在数据变化或视野变化时刷新，不逐帧重复画全部静态对象。
- 道路投影按视野缓存，不再每个对象、每个拖尾采样点都重新做地图投影。
- 相同路线与交通方式合并为共享轨迹；用缓存的 Path2D 绘制，移除每对象每帧多段 shadowBlur。
- 数值与 Vue 界面约每250ms更新，人物按目标30fps绘制，轨迹约15fps更新。两组情景仍保持同一出行需求。
- 地图拖动/缩放时暂缓重绘，结束后重建屏幕缓存；暂停时不持续重画不变的场景。

这些是具体实现变更，不是所有设备下稳定30fps的保证。未提供跨设备帧率对照测试，不写“性能提升百分比”。

## 展示与数据口径

展示页移除“情景仿真”“估算队列车辆”等反复提示，以“校园早高峰”“停车区近景”“停放数量”组织信息；不在页面宣称已经实采。接口仍保留 source=scenario_simulation、is_observed=false，实验报告与申报书必须据此区分生成需求、实采观测和反事实方案。

容载率=全部归属停车车辆/区域容量；违停率=区域外归属违停车辆/全部归属停车车辆。违停是总数子集，不能再加到停车总量。原习惯场景的热点有额外违停倾向，超出合法容量的车辆也列为违停，位置在对应区域外示意。停放位置不是测绘车位，也不能用于实测违法认定。

为避免除热点外全部空置，生成需求增加了区域覆盖分层：已有骑行队列中为各停车区保留到达需求，其他队列仍更集中于指定13个热点。两组保持相同起点、教学目的地、出发时刻及交通方式。初始仍可为0，播放后各区逐渐产生停放；不同于填固定数字到标签。

当前早高峰终点为教学楼；人进入教学楼后，已走过的完整道路轨迹保留60秒，再用30秒淡出。共享轨迹上若还有其他人在行进，会继续显示其轨迹。不是短光尾，也不使用辉光滤镜。
